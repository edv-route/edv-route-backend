## 1. Qué es este cambio (contexto de negocio)

Los registros que llegan **desde la app** ya no entran directo al padrón de afiliados: nacen como
**solicitud** (`applicant`) y el admin las revisa/aprueba en una sección **Solicitudes** aparte.
El registro por el **admin** no cambia. Flujo nuevo:

```
[App] Registro paso 1 (datos + cuenta + privacidad)            → applicant
[App] Completa solicitud: sube documentos + vehículos (incremental)
[Admin] Sección Solicitudes: revisa y aprueba/rechaza CADA documento y vehículo (con motivo)
[Admin] Aprobar solicitud (solo si TODO aprobado + ≥1 vehículo) → approved + deuda base (membresía + 1 sem)
[App] Paga (membresía + 1 sem + adelantar semanas) + acepta T&C
[Admin] Aprobar pago  +  Aprobar afiliado   (orden libre)
[Admin] "Establecer inicio" (modal: ahora / próximo lunes)     → ancla la tarifa → opera
```

**Decisión clave (desacople):** aprobar ≠ arrancar la tarifa. El afiliado puede quedar
`approved` **con deuda y sin operar** hasta que el admin **establece el inicio** (`startTariff`).

3. **Modal "Establecer inicio" automático** en ambos órdenes: al aprobar el afiliado (en el perfil)

4. **Card TARIFA "Sin iniciar"** oculta cobertura / próximo cobro (eran provisionales).
5. **Lista Afiliados**: badge tarifa "Sin iniciar" + estado "Pendiente de activación" para

## 5. Bugs encontrados y arreglados (críticos)

- 🐛 **Scheduler activaba la tarifa antes de establecer inicio**: el paso 3 de
  `subscription-scheduler` auto-arrancaba la suscripción `scheduled` de un `approved` en cuanto
  empezaba su semana; al establecer «próximo lunes» el re-anclaje no encontraba `scheduled` y las
  fechas quedaban en la semana en curso. **Fix**: `AND d.tariff_start_set_at IS NOT NULL`.
- 🐛 **Fechas de período provisionales (raíz)**: `enrollOnClient`/`enrollDebtOnClient` anclaban
  fechas ANTES del inicio y se re-anclaban después. **Fix de raíz** (migración
  `1752400000000_defer-period-dates`): `subscription_payments.period_start/period_end` → **nullable**;
  las semanas nacen **sin fechas (NULL)** y solo `enrollment.approve` (startTariff) las ancla. El
  re-anclaje ordena por `created_at` (antes por `period_start`, ahora NULL). **Principio de negocio:
  hasta establecer el inicio no existe NINGUNA fecha de tarifa en la BD, solo `created_at` y `paid_at`.**

- Registro paso 1 → `applicant` + token · gates negativos (applicant no paga 409, solicitud
  incompleta 409, pago sin T&C 400, `start-tariff` con deuda 409).
- Docs chofer (5,6,1) + vehículo + docs vehículo (9,7,10) + archivos (PNG) + imagen; checklist OK.
- Aprobación granular (6 docs + vehículo) → `approve-application` → `approved` + **deuda base $190**
  (membresía 180 + 1 semana 10), `tariff_start_set_at` NULL.
- Pago `purpose='debt'` → recibo `pending` → admin aprueba → **deuda 0**, membresía `paid`,
  `settledCharges: 2`.
- `start-tariff next_monday` → suscripción anclada al **lunes siguiente** (motor de deuda ON,
  semanal), `tariff_start_set_at` sellado, driver `scheduled`. Valida en vivo el fix de fechas (§5).
- El afiliado de prueba se **borró físicamente** (BD en cascada + 8 objetos de storage) tras la
  prueba; la BD compartida quedó intacta.

**⚠️ Hallazgo — el pago del app debe ir con `purpose='debt'`, NO `enroll`.** Tras
`approve-application` la deuda base ya crea un `membership_payment` pending, así que
`prepareEnrollContext` responde 409 ("ya tiene pago de membresía"). El *"adelantar semanas"* que
menciona el README §4.1 no encaja en este punto (`advance` exige suscripción `active`/`expired`,
que solo existe tras establecer inicio). **Acción sugerida:** alinear README §4.1/§6 y decidir si el
adelanto de semanas se ofrece **después** del arranque (con `advance`) o se elimina del alcance app.
