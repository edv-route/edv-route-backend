## 2. Lo que se hizo, por tema

### 2.1 Smoke E2E de "Solicitudes de la app" (Fase 1+2) — VERDE 45/45
Recorrido completo por API (registro paso 1 → docs+vehículo → aprobación granular →
`approve-application` (deuda base $190) → pago → aprobar pago → `start-tariff next_monday`). Gates
negativos OK. El afiliado de prueba se borró. **Hallazgo:** el pago del app debe ir con
`purpose='debt'` (NO `enroll`): tras `approve-application` la deuda base ya crea un `membership_payment`
pending y `prepareEnrollContext` responde 409. (Detalle en el HANDOFF del 2026-08-11 §11.)

### 2.2 Auditoría del panel admin — 4 bugs arreglados
Se auditó el contrato UI↔backend de las 22 pantallas. Arreglos:
- **[ALTA] `debt_engine_enabled` se guardaba como string** → apagaba el motor de deuda e
  **irreversible desde la UI** (el motor compara `=== true`). Fix en dos capas:
  - Frontend: `settings.ts`/`.html` tratan booleanos con un **toggle** (no texto); envían booleano real.
  - Backend: **coacción** en `settings.repository.ts` (`BOOLEAN_SETTING_KEYS`) — ningún cliente puede
    apagar el motor mandando texto. **Validado en vivo.**
- **[MEDIA] `request-detail.canApprove`** ahora replica `assertApplicationComplete` (carga
  `requirements` y exige que todo requisito obligatorio tenga documento aprobado).
- **[MEDIA] `billing-invoice-detail.html`** pinta el estado `overdue` ("En mora"), antes caía en
  "Emitida".
- **[MEDIA] Regla de formularios** `#f="ngForm"` + `markAllAsTouched()` en **requisitos**,
  **tipos de vehículo** y **editor de membresía** (más el mínimo de 3 en beneficios).

### 2.3 Reset total de la BD (autorizado) + Storage
- Se advirtió que la BD es la de **PRODUCCIÓN compartida** (Railway) con datos que parecían reales
  (12 afiliados con nombres/cédulas, dinero pagado). **El usuario confirmó** que son de prueba y pidió
  borrar directo. Se corrió `npm run db:reset` (preserva catálogos/membresía/tarifas/requisitos/
  métodos de pago/ajustes/**administradores**; reinicia numeración de facturas y recibos a 1) y se
  **vació el bucket privado** de Storage (178 objetos). Base en cero.

### 2.4 Toggle "Aprobar de inmediato" (autoApprove) en el registro
- El wizard dejaba el pago del alta **pendiente** a propósito (control anti-fraude v9). Se **expuso**
  el `autoApprove` que el backend ya soporta para el canal admin, como **toggle apagado por defecto**
  en el modal de pago del registro. Se **unificó** con el componente compartido `app-toggle`
  ("Aprobar de inmediato") que los 3 modales de pago del **perfil** ya usaban. Validado por API
  (registro admin diferido + submission enroll autoApprove → membresía `paid`, deuda 0).

### 2.5 Fix "Próximo cobro" (motor de deuda)
- La card de tarifa mostraba el **vencimiento** (lunes, `paidUntil`) como "próximo cobro". Con el
  motor ON, el cargo se **emite el viernes 18:00** (`billing_day_of_week=5`, `billing_hour=18`). Fix:
  - Backend: `DriversRepository.weeklyNextChargeAt(driverId)` calcula el **viernes de emisión** (la
    misma aritmética del `debt-scheduler`); `DriversService.getDetail` lo adjunta como
    `subscription.nextChargeAt` solo cuando el motor está ON + tarifa semanal activa.
  - Frontend: `driver-tariff-card` muestra ese día como "Próximo cobro" (en **días de calendario**,
    para que un cobro del viernes 18:00 lea "en 2 días"), y deja "Cobertura pagada hasta" para el
    vencimiento. Con el motor OFF vuelve al modelo prepago.

### 2.6 Múltiples pagos en revisión (cambio de fondo + migración)
- Antes: **un solo pago pendiente por afiliado** (índice único BD + `hasPending` + UI). Ahora el admin
  puede registrar **pagos separados** (cada uno cubriendo facturas distintas). **Regla de oro
  anti-doble-cobro:** cada factura la reserva **a lo sumo un** pago en revisión.
  - **Migración `1752410000000`** quita el índice único (APLICADA).
  - Backend: `PaymentSubmissionsRepository.reservedInvoiceIds(driverId)`; `create` valida
    no-solapamiento (un `debt` con `invoiceIds` solo si ninguna está reservada; otros propósitos
    siguen "uno a la vez"). `findDetail` expone `pendingCount`, `coveredInvoiceIds` (unión) y
    `pendingSubmissions` (array: `id, submissionNumber, amountUsd, purpose, createdAt, invoiceIds,
    invoiceNumbers`).
  - Frontend: `hasUnreservedDebt` (hay deuda no reservada → reaparece "Registrar pago" aunque haya
    pagos en revisión); el modal de pago ofrece solo facturas no reservadas. **Validado en vivo**
    (2º pago creado; blindaje rechaza factura ya reservada con 409).

### 2.7 Rediseño de pagos en revisión (cards + modal) + pipe de folios
- La banda plana pasó a **cards elegantes clickeables** (grid 1/2/3 col) en **dorado (`gold`)**:
  barra de acento, icono, badge "En revisión", monto grande, y **"Recibo N° 00009 · Factura N° 00015"**
  a la izquierda en negrita.
- **Componente nuevo `PaymentReviewModal`** (`features/billing/payment-review-modal.ts`/`.html`): al
  clic en una card, carga `PaymentSubmissionsApi.detail(id)` y muestra en **modal ancho (`max-w-4xl`)**:
  cabecera dorada con **texto gris oscuro** (buen contraste), datos del pago, y **dos columnas** —
  izquierda "Qué cubre" (facturas + total), derecha "Comprobante" (imagen grande `object-contain`,
  zoom a pantalla completa; placeholder si no hay). Tiene **skeleton de carga** y badge blanco legible.
- **Pipe `folio`** (`shared/pipes/folio.pipe.ts`, con función `padFolio`): rellena números de factura/
  recibo con **ceros a 5 dígitos** (`15 → 00015`; ≥5 dígitos intacto). **Solo visual**; no toca la
  numeración continua. Aplicado en **8 componentes / 13 usos** + el método `invoiceLabel`.
- Textos: "al aprobarlo salda su deuda" → "salda **lo que cubre**" (impreciso en pago parcial).
